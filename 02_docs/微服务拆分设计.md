# 微服务拆分设计

## 1. 设计目标

小学期要求学习并实践微服务拆分、性能追踪监控等重构和优化技术。考虑到项目周期较短，本项目采用稳定增强路线：在保留现有系统可运行的前提下，先完成模块边界梳理、接口规范化、公共能力抽取和网关设计，再逐步拆分核心服务。

## 2. 当前架构

当前系统为前后端分离单体后端架构：

```text
React/Vite 前端
       |
       v
Express 单体后端
       |
       v
MySQL
```

后端模块包括：

- 用户与认证。
- 商品与二手商品。
- 订单。
- 评价。
- 店铺。
- 地址。
- 聊天议价。
- 上传。

## 3. 目标架构

稳定路线下的目标架构如下。中期检查采用 `微服务接口与数据归属.md` 中的 `MS-SPLIT` 图作为权威划分图，接口状态和逐表归属也以该文档为准。

```text
Frontend
   |
API Gateway
   |
   +-- user-service
   +-- product-service
   +-- order-service
   +-- evaluation-service
   +-- chat-service
   +-- file-service
   |
 MySQL / Cache / Object Storage
```

小学期实际落地优先级：

| 优先级 | 服务 | 说明 |
| --- | --- | --- |
| P0 | API Gateway | 统一鉴权、限流、日志、路由 |
| P0 | user-service | 登录、注册、用户信息、信用信息 |
| P0 | product-service | 商品、二手商品、搜索、推荐 |
| P0 | order-service | 下单、订单状态、物流信息 |
| P1 | product-service | 店铺资料与商品发布资格归入商品域 |
| P1 | evaluation-service | 评价和评分 |
| P2 | chat-service | 聊天和议价 |
| P2 | file-service | 文件上传和存储 |

## 4. 拆分边界

### 4.1 用户服务

职责：

- 注册、登录、JWT 签发。
- 用户资料管理。
- 密码修改。
- 信用等级和信用分维护。

接口示例：

```text
POST /api/users/register
POST /api/users/login
GET  /api/users/profile
PUT  /api/users/profile
PUT  /api/users/password
```

### 4.2 商品服务

职责：

- 商品列表、详情、搜索。
- 二手商品发布和管理。
- 商品推荐。
- 库存和商品状态。

接口示例：

```text
GET    /api/products
GET    /api/products/:id
POST   /api/products
PUT    /api/products/:id
DELETE /api/products/:id
```

### 4.3 订单服务

职责：

- 创建订单。
- 订单查询。
- 订单状态更新。
- 物流信息维护。
- 下单库存扣减。

接口示例：

```text
POST /api/orders
GET  /api/orders
GET  /api/orders/:id
PUT  /api/orders/:id/status
```

### 4.4 API 网关

职责：

- 统一入口。
- JWT 鉴权。
- CORS。
- 限流。
- 请求日志。
- Trace ID。
- 路由转发。

## 5. 数据库策略

短期稳定方案：

- 仍使用同一个 MySQL 数据库。
- 按服务边界管理模型和访问逻辑。
- 不在小学期内强制拆分多个数据库。

长期演进方案：

- 用户服务独立用户库。
- 商品服务独立商品库。
- 订单服务独立订单库。
- 服务间通过 API 或消息事件同步必要数据。

## 6. 重构步骤

1. 梳理路由、控制器、模型和业务职责。
2. 提取公共中间件：鉴权、错误处理、日志、限流。
3. 统一接口响应格式。
4. 设计 API 网关路由规则。
5. 优先将用户、商品、订单模块拆分为独立目录或服务原型。
6. 保持前端 API 地址兼容，减少前端改动。
7. 对拆分后的核心接口执行回归测试。

## 7. 风险控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 拆分过多导致无法运行 | 影响演示 | 只拆核心模块或提供网关原型 |
| 服务间调用复杂 | 增加调试成本 | 短期保留共享数据库和同步调用 |
| 前端接口变动过大 | 影响功能 | 网关保持原 API 路径兼容 |
| 数据一致性问题 | 影响订单和库存 | 下单逻辑继续使用数据库事务 |

## 8. 小学期验收方式

- 提供拆分设计文档。
- 提供模块化代码提交记录。
- 演示 API 网关或核心服务拆分原型。
- 展示重构前后的模块结构对比。
- 展示核心功能回归测试结果。
