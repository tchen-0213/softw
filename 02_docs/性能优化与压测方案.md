# 性能优化与压测方案

## 1. 目标

本方案用于支撑小学期对高性能和高并发能力的要求。目标是在不大幅改变现有技术栈的前提下，通过数据库索引、查询优化、缓存设计、并发控制、压测验证和监控记录提升系统性能。

## 2. 重点接口

| 接口 | 风险 | 优化重点 |
| --- | --- | --- |
| POST /api/users/login | 高频访问 | 限流、密码校验耗时监控 |
| GET /api/products | 高频列表查询 | 分页、索引、缓存 |
| GET /api/products/:id | 高频详情查询 | 缓存、浏览量异步化 |
| GET /api/products/recommended | 首页推荐 | 缓存 |
| POST /api/orders | 并发下单 | 事务、库存扣减、超卖控制 |
| GET /api/orders/seller | 卖家订单 | 避免全表扫描和内存过滤 |

## 3. 数据库优化

建议索引：

```sql
CREATE INDEX idx_products_status_created_at ON Products(status, createdAt);
CREATE INDEX idx_products_category_status ON Products(category, status);
CREATE INDEX idx_products_secondhand_status ON Products(isSecondhand, status);
CREATE INDEX idx_products_seller_status ON Products(sellerId, status);
CREATE INDEX idx_products_sales_rating ON Products(sales, rating);

CREATE INDEX idx_orders_user_status_created_at ON Orders(userId, status, createdAt);
CREATE INDEX idx_orders_status_created_at ON Orders(status, createdAt);

CREATE UNIQUE INDEX idx_users_email ON Users(email);
CREATE UNIQUE INDEX idx_users_username ON Users(username);
```

说明：

- 商品列表常按状态、分类、是否二手、创建时间查询。
- 用户订单常按 userId、status、createdAt 查询。
- 用户登录常按 email 查询。
- 实际索引创建需结合数据库已有索引，避免重复创建。

## 4. 查询优化

### 4.1 商品列表

当前商品列表已经支持分页，需继续保持最大 `limit` 不超过 100，避免一次性返回过多数据。

优化建议：

- 保持分页参数上限。
- 对 `category`、`status`、`isSecondhand` 建索引。
- 热门分类结果可短时间缓存。

### 4.2 卖家订单

当前卖家订单存在先查询所有订单再在内存中过滤的风险。数据量增加后会导致响应变慢。

优化方向：

- 在订单项中冗余 sellerId 后，可增加订单卖家关联表。
- 或将订单按买家订单和卖家订单拆表/建视图。
- 短期可增加分页并减少返回字段。

### 4.3 商品详情浏览量

商品详情接口会同步增加浏览量。高并发访问时可能增加数据库写压力。

优化方向：

- 短期保留同步更新。
- 中期可使用缓存计数，定时批量写回数据库。

## 5. 缓存设计

建议缓存对象：

| 缓存内容 | TTL | 失效条件 |
| --- | --- | --- |
| 首页推荐商品 | 60 秒 | 商品新增、下架、销量变化 |
| 热门分类商品列表 | 30 秒 | 商品状态或分类变化 |
| 商品详情 | 60 秒 | 商品编辑、下架 |

小学期稳定路线下，可以先完成缓存设计文档，后续接入 Redis。

## 6. 并发下单控制

订单创建接口已经使用数据库事务，但需要进一步关注库存扣减的并发安全。

建议方案：

- 在事务中查询商品并扣减库存。
- 增加库存条件更新：只有 `stock >= quantity` 时才更新成功。
- 二手商品库存归零后更新为“已预订”或“已售出”。
- 压测并发下单场景，验证不会出现负库存。

## 7. 压测工具

建议使用 k6 或 Apache JMeter。若需要命令行脚本，优先使用 k6。

核心指标：

- QPS。
- 平均响应时间。
- P95 响应时间。
- 错误率。
- CPU 和内存占用。
- 数据库连接数。

## 8. 压测场景

| 场景 | 并发用户 | 持续时间 | 目标 |
| --- | --- | --- | --- |
| 商品列表查询 | 50 | 3 分钟 | 错误率低于 1%，P95 小于 1000ms |
| 商品详情查询 | 50 | 3 分钟 | 错误率低于 1%，P95 小于 1000ms |
| 用户登录 | 20 | 2 分钟 | 错误率低于 1%，P95 小于 1500ms |
| 创建订单 | 20 | 2 分钟 | 不出现负库存，错误提示合理 |

## 10. 验收标准

- 至少完成 3 个核心接口压测。
- 输出压测数据和结论。
- 说明性能瓶颈和优化措施。
- 至少完成数据库索引或查询优化设计。
- 并发下单场景不出现负库存。

## 11. 已落地优化项

当前代码已完成以下性能相关优化：

- 卖家订单查询增加分页返回。
- 卖家订单查询避免原先全量 `Order.findAll()` 后在内存中过滤。
- 新增卖家订单 DTO 单元测试，确保只返回当前卖家的订单项。
- 保留 `k6-core-flow.js` 作为快速基准脚本。
- 新增 `k6-interface-comparison.js`、固定数据脚本和自动资源采样，对 3 个商品接口完成两个版本各 3 次实测。
