## 第 4 页 · 模型到代码

以 UC04 为例，三层模型对应到不同粒度的实现。系统级只保留买家、卖家和下单、支付、发货、收货这条闭环；组件级才出现结账页、鉴权中间件、`orderController` 和事务；对象级的 `createOrder()`、`pay`、`ship`、`confirm` 和源码里的函数名是对上的。

| 层次 | 模型里有什么 | 落到代码 | 图 |
| --- | --- | --- | --- |
| 系统级 SYS-SEQ04 | 买家、卖家；下单、支付、发货、收货 | 从创建订单到确认收货的业务闭环 | SYS-SEQ04 |
| 组件级 COMP-SEQ04 | 结账页、鉴权、订单控制器、模型、事务 | `orderController`、`CheckoutPage` | COMP-SEQ04 |
| 对象级 OBJ-SEQ04 | `createOrder()`、库存扣减、pay / ship / confirm | 与源码函数名一致 | OBJ-SEQ04 |

订单状态是待付款 → 待发货 → 待收货 → 已完成，中途可以取消。拆分之后，order-service 不直接改库存表，而是带着 `reservationId` 去调 product-service 做预留、释放和完成。

## 第 5 页 · 业务微服务：职责、划分依据、接口、表归属

调用链是前端先打到 API 网关，再转到三个业务服务。拆分按身份、可交易资源和交易过程来，评价、聊天、图片上传放在商品服务里。网关只做入口，不占一个业务库。

| 服务 | 职责 | 划分依据 | 库与表 |
| --- | --- | --- | --- |
| user-service | 注册登录、资料、密码、地址、角色、信用 | 身份和账号生命周期 | `softw_users`：Users、Addresses |
| product-service | 商品、二手、店铺、评价、聊天、议价、图片、库存 | 可交易的资源 | `softw_catalog`（Products、Shops、Evaluations、Chat*、InventoryReservations）+ `uploads/` |
| order-service | 下单、支付、取消、发货、收货、状态机 | 交易过程和订单快照 | `softw_orders`：Orders、OrderSellers |
| API 网关 | 路由、JWT 透传、超时、CORS | 统一入口 | 无库 |

网关前缀：`/api/users`、`/api/addresses` 进用户服务；商品、二手、店铺、评价、聊天、上传进商品服务；`/api/orders` 进订单服务。三张业务库在同一台 MySQL 上，库名隔开。一张表只由一个服务写；下单时把商品项和地址做成快照存进订单，不跨库联表。订单向商品预留库存、商品或订单向用户取身份和信用，走内部接口，请求要带 `X-Internal-Token`。

## 第 6 页 · 调用失败时的处理办法

跨服务调用失败时，按场景返回事先定好的状态，而不是把失败包装成下单成功。

| 场景 | 处理 |
| --- | --- |
| 网关超时或上游断开 | 返回 HTTP 503 |
| 库存预留失败（无货或对端超时） | 不创建订单；超时返回 503 |
| 释放 / 完成预留 | 按 `reservationId` 幂等，重复调用不会把库存加第二次 |
| 停掉 product-service | 商品接口 503，提示「依赖服务暂不可用」；订单依赖检查 206，`status=degraded`，提示「商品信息暂不可用，订单查询保持可用」；网关、用户、订单仍是 1/1 |
| 内部库存、信用、购买证明 | 必须带 `X-Internal-Token`，外部请求进不了这些接口 |

故障实验用 `npm run experiment:fault`。停掉商品服务看 503 和 206，拉起来之后商品接口回到 200，副本会重建，没有残留的失败副本。
