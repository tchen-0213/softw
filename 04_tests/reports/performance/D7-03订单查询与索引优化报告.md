# D7-03 订单查询与索引优化报告

实验日期：2026-08-31

## 1. 结论

D7-03 已将微服务卖家订单查询从“读取全部订单后在 Node.js 内存过滤”改为数据库层索引连接、计数和分页。
在同一台机器、同一 MySQL 8.0.46 实例、同一批 20,000 条订单、同一 Node.js 进程下执行 7 轮前后对比：

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 平均耗时 | 307.554 ms | 4.587 ms | 降低 98.509% |
| P95 | 341.074 ms | 5.201 ms | 降低 98.475% |
| 单次加载到应用的订单行数 | 20,000 | 20 | 降低 99.9% |
| 返回结果 | 20 条 | 20 条 | 7 轮 ID 完全一致 |

该结果证明当前实现消除了卖家订单接口的无界全表加载；它只适用于本报告的机器、数据量和查询条件，
不外推为所有部署环境下的固定提升比例。

## 2. 实现内容

### 2.1 卖家订单数据库查询

- 新增 `OrderSellers(orderId, sellerId)` 映射表，使用复合主键防止重复关系。
- 新增 `idx_order_seller_lookup(sellerId, orderId)`，卖家查询先按卖家索引定位订单。
- `/api/orders/seller` 在数据库层执行筛选、计数、排序、`offset` 和 `limit`，应用层只处理当前页。
- 新订单在同一数据库事务内同时写入订单和卖家映射，避免订单与查询映射不一致。
- 服务启动时以每批 500 条的方式为旧订单幂等回填映射，不进行一次性无界加载。

### 2.2 核心索引复核

| 服务 | 索引 | 对应路径 |
| --- | --- | --- |
| order-service | `idx_order_seller_lookup(sellerId, orderId)` | 卖家订单筛选与分页 |
| order-service | `idx_orders_buyer_status_created(userId, status, createdAt)` | 买家订单、状态筛选和时间排序 |
| order-service | `idx_orders_status_created(status, createdAt)` | 订单状态与时间查询 |
| product-service | `idx_products_catalog_filter(status, category, isSecondhand, price)` | 商品分页、分类、二手和价格筛选 |
| product-service | `idx_products_recommended(status, sales, rating)` | 推荐商品排序 |
| product-service | `idx_products_seller_updated(sellerId, status, updatedAt)` | 卖家商品管理 |
| user-service | `email`、`username` 唯一索引 | 登录和注册查重 |
| user-service | `idx_addresses_user_default_updated(userId, isDefault, updatedAt)` | 用户地址列表 |

初始化逻辑会读取现有索引并只补建缺失的具名索引，因此已有数据库无需删除表或使用 `sync({ alter: true })`。
执行计划确认卖家订单、商品筛选、用户登录和地址查询分别命中
`idx_order_seller_lookup`、`idx_products_catalog_filter`、`email` 和
`idx_addresses_user_default_updated`。

### 2.3 并发与一致性

- 下单库存预留继续使用数据库事务和 `SELECT ... FOR UPDATE` 行锁。
- `InventoryReservation.id` 作为幂等键，防止同一预留重复扣减。
- 新增并发回归：库存为 1 时两个不同预留同时请求，只有一个返回 201，另一个返回 400；最终库存为 0，
  只保留一条预留记录，不出现超卖、负库存或脏预留。
- 新增同一幂等键并发回归：两个请求分别返回 201 和 200，共享同一预留，库存只扣减一次；预留事务使用
  `READ COMMITTED` 并在取得商品行锁后再次检查幂等记录，避免并发唯一键冲突退化为 500。
- 本次未引入缓存。订单状态和库存属于强一致数据；当前索引查询已达到毫秒级，引入缓存会增加 TTL、失效和
  跨服务补偿复杂度，缺少收益证据，因此明确不使用缓存。

## 6. 限制

- 本次量化聚焦已识别的卖家订单查询缺口，使用单机 MySQL 和 20,000 条固定订单。
- 前后对比包含旧实现的数据库读取、JSON 解析和内存过滤全过程，也包含新实现的分页查询与总数查询。
- 公网延迟、多节点数据库和更大规模数据需要在目标部署环境另行测试。
