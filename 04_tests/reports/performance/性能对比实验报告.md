# 单体与微服务性能对比实验报告

实验日期：2026-08-28

## 1. 实验结论

本次实验在同一台机器、同一 Docker 引擎、同一批 200 条固定商品数据上，使用同一份 k6 脚本，
分别对单体和微服务的 3 个主要商品接口各运行 3 次。18 个 case 全部通过，错误率均为 0%。

| 接口 | 微服务吞吐量变化 | 微服务平均延迟变化 | 微服务平均 CPU 变化 | 微服务平均内存变化 |
| --- | ---: | ---: | ---: | ---: |
| 商品列表 | +61.9% | -38.6% | +55.2% | +5.1% |
| 商品搜索 | +53.9% | -35.5% | +50.7% | +17.3% |
| 商品详情 | +30.9% | -26.2% | +6.9% | +14.0% |

可以得出的结论是：**在本次限定条件下，当前微服务实现的三个商品查询接口吞吐量更高、响应延迟更低，
但服务端总 CPU 和内存开销更高。**不能据此写“微服务架构天然更快”。

## 6. 差异分析

1. 单体商品列表会关联查询 `Users` 表并组装卖家对象；微服务商品表保存卖家快照，查询路径更聚焦。
   在当前固定数据和只读接口上，这部分差异超过了 API Gateway 多一次转发的成本。
2. 微服务版本的 Express 中间件和商品控制器更精简；单体还执行全局安全、限流、请求追踪及较完整的
   ORM 关联处理，因此本次延迟更高。它们是当前实现差异，不能直接归因于“拆成微服务”。
3. 微服务需要同时运行网关和商品服务两个 Node.js 进程，且使用独立 MySQL 容器，因此三个接口的
   内存均高于单体，列表和搜索的 CPU 也明显更高。这是拆分和额外网络/序列化带来的资源成本。
4. 详情接口两边都会增加浏览次数，包含一次数据库写操作；该接口的微服务 CPU 优势很小，说明涉及
   写操作后，两种实现的差距比纯查询更小。

## 7. 原始证据与复现

```bash
npm run perf:compare
```

脚本会自动写入同一批数据、校验两边 MD5、执行 18 个 case、生成 CSV，并在退出时清理实验数据。

- 汇总 CSV：`04_tests/reports/performance/interface-comparison-2026-08-28.csv`
- 原始目录：`04_tests/reports/performance/raw/interface-comparison-2026-08-28/`
- 每个 case 的 `.json`：k6 机器可读指标。
- 每个 case 的 `.txt`：k6 原始控制台报告。
- 每个 case 的 `-stats.tsv`：逐时间点、逐容器 CPU 和内存。
- `dataset-verification.txt`：两边数据数量、ID 范围和 MD5 校验结果。

限制：这是单机 Docker、5 VU、20 秒的短时实验，不代表公网延迟、多节点 Kubernetes 或长期稳定性。
结论只适用于本报告的代码版本、数据规模、接口和运行环境。
